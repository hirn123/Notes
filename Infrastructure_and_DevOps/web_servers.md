# Веб-серверы: назначение, виды и обработка запросов

## 1. Что такое веб-сервер

**Веб-сервер** — это программное обеспечение, которое прослушивает сетевой порт (обычно 80 для HTTP и 443 для HTTPS), принимает HTTP-запросы от клиентов (браузеров) и возвращает HTTP-ответы.

Ответ может быть:
- **Статическим файлом** (HTML, CSS, изображение, JS), который уже существует на диске.
- **Сгенерированной страницей**, созданной приложением «на лету».
- **Данными для API** (например, JSON).

Термин также используется для обозначения самой машины, на которой работает это ПО, но в контексте конфигурации и диагностики речь всегда идёт о программе.

**Ключевые задачи веб-сервера:**
- Приём и обработка HTTP/HTTPS-запросов.
- Отдача статических файлов (изображения, CSS, шрифты).
- Перенаправление динамических запросов обработчикам (PHP, Python, Node.js).
- Кэширование контента для ускорения загрузки.
- Ведение логов доступа и ошибок.
- Маршрутизация URL и защита от несанкционированного доступа.

## 2. Популярные веб-серверы

| Сервер | Особенности | Платформа |
|---|---|---|
| **Apache HTTP Server** | Один из старейших (с 1995 г.). Гибкий, модульный, поддерживает `.htaccess`. Высокая совместимость с CMS | Кроссплатформенный |
| **Nginx (engine x)** | Высокая производительность, событийная архитектура. Часто используется как reverse proxy и балансировщик нагрузки | Кроссплатформенный |
| **Microsoft IIS** | Тесно интегрирован с Windows Server. Оптимален для ASP.NET приложений | Windows |
| **Caddy** | Современный сервер (с 2015 г.). Автоматическое получение и обновление HTTPS-сертификатов, простой синтаксис конфигурации | Кроссплатформенный |
| **LiteSpeed** | Коммерческий сервер с высокой скоростью и низким потреблением ресурсов. Есть open-source версия (OpenLiteSpeed) | Кроссплатформенный |

На 2025 год лидируют Nginx (~34%) и Apache (~26%).

## 3. Как веб-сервер обрабатывает HTTP-запрос

Жизненный цикл запроса проходит несколько этапов:

1. **Прослушивание порта (Listen).** Сервер открывает порт и ожидает TCP-подключения.
2. **Приём и расшифровка (Accept & Decrypt).** Приходит соединение. Если используется HTTPS, выполняется TLS-рукопожатие с использованием сертификата домена.
3. **Чтение запроса (Read).** Сервер читает метод (GET, POST), путь (`/products/42`), заголовки (`Host`, `Cookie`, `Accept`) и, при наличии, тело запроса.
4. **Решение (Decide).** Заголовок `Host` определяет, какой сайт обслуживать. Путь определяет, нужно ли прочитать файл с диска или передать запрос приложению.
5. **Ответ (Respond).** Сервер отправляет статус-код (200, 404, 500), заголовки (`Content-Type`, `Cache-Control`) и тело ответа.
6. **Логирование (Log).** Запись в лог доступа: IP клиента, путь, статус-код, время выполнения.

**Пример диалога:**
```http
GET /index.html HTTP/1.1
Host: example.com
Accept: text/html
```
```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1256
Cache-Control: max-age=3600

<!doctype html>...
```

Если что-то идёт не так, статус-код указывает на проблему: `404` — файл или маршрут не найден, `502` — веб-сервер не может получить ответ от приложения за ним.

## 4. Режимы работы: статический сервер, сервер приложений, reverse proxy

| Роль | Что делает | Пример |
|---|---|---|
| **Статический сервер** | Отдаёт готовые файлы с диска (HTML, CSS, картинки) | Nginx, отдающий `/var/www/static/style.css` |
| **Сервер приложений** | Выполняет код (PHP, Python, Node.js) и генерирует страницу | PHP-FPM, Gunicorn, Node.js process |
| **Reverse proxy (обратный прокси)** | Принимает запрос от клиента и перенаправляет его другому серверу (обычно приложению), скрывая его от клиента | Nginx перед Gunicorn или Apache |

**Важно:** один и тот же сервер (например, Nginx) может выполнять все три роли одновременно, в зависимости от конфигурации.

## 5. Файл `.htaccess` (только для Apache)

**`.htaccess`** — это файл конфигурации уровня директории, который позволяет изменять настройки Apache **без доступа к главному конфигу сервера** (`httpd.conf`).

**Где применяется:** Директивы из `.htaccess` действуют на ту директорию, в которой лежит файл, и на все её поддиректории.

**Типичные задачи, которые решают через `.htaccess`:**
- **Управление доступом:** запрет доступа к директории (`deny from all`), базовая HTTP-аутентификация.
- **URL-rewriting (ЧПУ):** преобразование `example.com/product/42` в `example.com/product.php?id=42` через `RewriteRule`.
- **Server Side Includes (SSI):** вставка общего футера или шапки на все страницы (`<!--#include virtual="/footer.html" -->`).
- **Кэширование и сжатие:** настройка заголовков `Cache-Control`, включение gzip.

**Ключевое ограничение:** `.htaccess` работает **только на Apache**. Nginx не поддерживает `.htaccess`; все директивы должны быть прописаны в основном конфиге сервера.

**Почему `.htaccess` считается «костылём»:** при каждом запросе Apache вынужден проверять наличие `.htaccess` во всех директориях по пути к файлу, что создаёт дополнительную нагрузку. Официальная документация Apache рекомендует использовать `.htaccess` только тогда, когда у пользователя нет доступа к основному конфигу (типичный случай на Shared-хостинге).

## 6. Apache vs Nginx: ключевые различия

| Параметр | Apache | Nginx |
|---|---|---|
| **Архитектура** | Процесс/поток на каждое соединение (prefork/worker MPM) | Событийная (event-driven), один процесс обрабатывает множество соединений |
| **Производительность под нагрузкой** | Снижается при большом числе одновременных соединений, потребляет больше памяти | Стабильная, хорошо масштабируется, эффективно использует память |
| **Статические файлы** | Работает, но медленнее | Значительно быстрее |
| **Динамический контент** | Встроенная поддержка PHP (mod_php), множество модулей | Обычно передаёт запросы приложению (PHP-FPM, Gunicorn) через FastCGI или сокет |
| **`.htaccess`** | Поддерживает | Не поддерживает |
| **Гибкость / модули** | Огромное количество модулей, расширяемость | Меньше модулей, но достаточно для большинства задач |
| **Конфигурация** | Сложная, но очень гибкая | Более простая и декларативная |

**Когда что выбирать:**
- **Apache** — когда нужна максимальная совместимость с legacy-приложениями, `.htaccess` (типично для Shared-хостинга) или когда требуется специфический модуль Apache.
- **Nginx** — когда важна производительность под нагрузкой, раздача статики, работа в качестве reverse proxy или балансировщика.

---

## 7. Связка Apache + Nginx

На многих хостингах (особенно в связке с панелями управления, такими как ISPmanager или Plesk) Apache и Nginx работают **вместе**.

**Схема работы:**
1. **Nginx** принимает запрос от клиента.
2. Если запрос **статический** (картинка, CSS, JS), Nginx отдаёт файл сразу.
3. Если запрос **динамический** (например, `/index.php`), Nginx передаёт его **Apache** как reverse proxy.
4. Apache передаёт запрос обработчику (PHP-FPM), получает сгенерированный файл и возвращает его Nginx.
5. Nginx отправляет финальный ответ клиенту.

**Преимущества:** Nginx быстро отдаёт статику и держит нагрузку, а Apache обеспечивает совместимость с `.htaccess` и привычными модулями для динамических сайтов. Это компромисс между производительностью и гибкостью.
