# API (Application Programming Interface)

## 1. Определение

**API** — это программный интерфейс приложения. Набор правил и инструментов, с помощью которых одна программа может взаимодействовать с другой, не имея доступа к её внутренней реализации.

> **Аналогия (ресторан):**
> - Клиент (одна программа) делает заказ.
> - Официант (API) принимает заказ по строгим правилам и передаёт его.
> - Кухня (бэкенд/база данных) готовит еду.
> - Клиент не имеет доступа к кухне и не знает, как именно готовится блюдо, но получает результат.

## 2. Зачем нужен API

- **Изоляция** — скрывает внутреннюю логику и базу данных от прямого доступа.
- **Безопасность** — разрешает выполнение только строго определённых операций.
- **Интеграция** — позволяет приложениям (например, мобильному приложению и серверу) обмениваться данными.

## 3. REST API (самый популярный стандарт)

**REST** (Representational State Transfer) — архитектурный стиль, где взаимодействие строится вокруг ресурсов (объектов) и HTTP-методов (CRUD).

| Метод | Назначение | Пример |
|---|---|---|
| `GET` | Получение данных | `GET /users/1` |
| `POST` | Создание нового объекта | `POST /users` |
| `PUT` / `PATCH` | Обновление объекта (PUT — полная замена, PATCH — частичное) | `PUT /users/1` |
| `DELETE` | Удаление объекта | `DELETE /users/1` |

## 4. Структура API-запроса

1. **URL (Endpoint)** — адрес ресурса, например `https://api.github.com/users/torvalds`.
2. **Метод HTTP** — `GET`, `POST`, `PUT`, `DELETE`.
3. **Заголовки (Headers)** — служебная информация (тип передаваемых данных, авторизация).
4. **Тело (Body)** — передаваемые данные (используется в `POST` и `PUT`).

### 4.1. Авторизация в API
API не пустит просто так. В отличие от сайтов, где ты вводишь логин/пароль, программы общаются через **токены**.
В заголовке передается ключ доступа:
`Authorization: Bearer <твой_токен_или_API_ключ>`
Если токен неверный или просрочен, API вернет код **401 Unauthorized** или **403 Forbidden**.

## 5. Формат данных: JSON

Стандартный формат обмена данными в современных API. Представляет собой текстовый формат, похожий на словари в Python.

```json
{
  "id": 1,
  "name": "Ivan",
  "role": "admin"
}
```

## 6. Ответы API (HTTP-коды)
API использует те же HTTP-коды ответов, что и обычные сайты. Сисадмину важно их знать при диагностике:
- **200 OK** — Запрос успешно выполнен (данные получены или обновлены).
- **201 Created** — Объект успешно создан (ответ на POST).
- **400 Bad Request** — Ошибка в запросе (например, отправили текст вместо числа).
- **401 Unauthorized** — Не передан токен авторизации.
- **403 Forbidden** — Токен есть, но прав на это действие нет.
- **404 Not Found** — Такого ресурса (URL) не существует.
- **500 Internal Server Error** — Ошибка на стороне сервера API (бэкенд упал).

## 7. Инструменты для работы с API

*   **Swagger (OpenAPI):** Стандарт **документации** для API. Разработчики пишут описание (в формате YAML/JSON), а Swagger генерирует красивую веб-страницу. Сисадмин или тестировщик открывает её и видит: какие есть эндпоинты, какие параметры нужно передать и что вернется в ответ.
*   **Postman:** Программа-клиент (с графическим интерфейсом) для тестирования API. Позволяет удобно сохранять историю запросов, передавать токены и смотреть ответы в формате JSON.
*   **curl:** Консольная утилита. Позволяет отправлять API-запросы прямо из терминала (идеально для написания bash-скриптов и автоматизации).

## 8. Практика с curl

**1. Получить данные пользователя GitHub (GET):**
```bash
curl -s https://api.github.com/users/torvalds
```

**2. Посмотреть статус-код ответа:**
```bash
curl -I https://api.github.com/users/torvalds
```
*(Ожидаемый ответ: `HTTP/2 200`)*

**3. Проверка ошибки 404 (несуществующий пользователь):**
```bash
curl -I https://api.github.com/users/asdasdasd-qweqwe123
```
*(Ожидаемый ответ: `HTTP/2 404`)*

**4. Форматирование JSON-ответа для удобного чтения:**
```bash
curl -s https://api.github.com/users/torvalds | python3 -m json.tool
```
