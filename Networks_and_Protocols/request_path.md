Задача: Что происходит, когда я ввожу https://example.com в адресную строку и нажимаю Enter?

1. Проверка кэша (Browser & OS)
Браузер сначала не лезет в интернет, а проверяет: «А может, я уже знаю этот сайт?».
Ищет в кэше браузера (история, куки, кэш DNS).
Если нет, спрашивает операционную систему (Windows/Linux). ОС проверяет свой файл hosts и системный DNS-кэш.
Если нигде нет — идет дальше в алгоритме.

2. DNS-резолвинг (Поиск IP-адреса)
Браузеру нужен IP-адрес сервера, ведь по проводам бегают только IP, а не буквы.
Браузер отправляет запрос локальному DNS-серверу (обычно это роутер или провайдер).
Если провайдер не знает, запрос идет вверх по иерархии: Корневые серверы -> Серверы зоны .com -> Авторитативные серверы домена example.com.
Результат: Браузер получает IP-адрес (например, 93.184.216.34).

3. TCP Handshake (Установка соединения)
Браузер знает IP, теперь нужно установить надежное соединение (TCP) на порт 443 (для HTTPS).

Я уже видел это в Wireshark:

Браузер: SYN (я хочу соединиться).
Сервер: SYN-ACK (я согласен).
Браузер: ACK (принято).
Соединение установлено.

4. TLS Handshake (Шифрование HTTPS)
Раз мы используем HTTPS, нужно договориться о шифровании, чтобы никто не подслушал трафик.

Браузер отправляет Client Hello (поддерживаемые версии TLS, шифры).
Сервер отвечает Server Hello и присылает свой SSL-сертификат.
Браузер проверяет сертификат (не истек ли срок, выдан ли он удостоверяющим центром, совпадает ли имя домена).
Стороны обмениваются ключами. С этого момента трафик зашифрован.

5. HTTP-запрос
Теперь браузер может безопасно попросить страницу.

Отправляется текст: GET / HTTP/1.1 (или HTTP/2).
Вместе с ним летят заголовки (Headers):

Host: example.com (какой сайт мы просим).
User-Agent: Chrome... (какой у меня браузер).
Cookie: ... (мои данные авторизации/настроек).
Accept: text/html (я хочу HTML).

6. Обработка на сервере (Nginx / Apache)
Запрос долетает до сервера. Там его встречает веб-сервер (обычно Nginx или Apache).

Nginx смотрит на запрос. Если это статичный файл (картинка, CSS, просто HTML), он отдает его сразу.
Если запрос требует логики (авторизация, поиск по базе), Nginx работает как прокси (reverse proxy) и передает запрос Бэкенду (Python, PHP, Node.js) через внутренний порт (например, 8080 или через unix-socket).

7. Работа Бэкенда (Backend & Database)
Бэкенд (например, на Python/Django) принимает запрос.

Он выполняет код: проверяет куки, достает данные из Базы Данных (PostgreSQL/MySQL).
Бэкенд собирает HTML-страницу (например, через шаблонизатор) и отдает её обратно Nginx'у.

8. HTTP-ответ (Response)
Nginx формирует ответ и отправляет его браузеру.

Статус-код: 200 OK (если всё хорошо) или 404 Not Found (если бэкенд не нашел страницу).
Заголовки: Content-Type: text/html, Set-Cookie (если сервер хочет поставить новую куку).
Тело ответа: Сам HTML-код страницы.

9. Парсинг и рендеринг (Browser Rendering)
Браузер получает HTML и начинает его «читать».

Строит DOM-дерево.
Находит внутри HTML ссылки на картинки, CSS-стили и JS-скрипты.
Важно: Для каждой картинки и скрипта браузер снова выполняет Шаги 2, 3, 4 и 5 (заново ищет IP, ставит TCP/TLS соединение и делает запрос), если они не закэшированы.
Браузер применяет CSS, выполняет JS и отрисовывает сайт на экране.
