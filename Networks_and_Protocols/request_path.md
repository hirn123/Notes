# Что происходит, когда я ввожу `https://example.com` и нажимаю Enter

## 1. Проверка кэша (Browser & OS)

Браузер сначала не лезет в интернет, а проверяет, не знает ли он уже этот сайт:
- кэш браузера (история, куки, DNS-кэш);
- если нет — спрашивает ОС (Windows/Linux), которая смотрит файл `hosts` и системный DNS-кэш.

Если нигде нет — идём дальше.

## 2. DNS-резолвинг (поиск IP-адреса)

Браузеру нужен IP сервера: по проводам бегают IP, а не буквы.

1. Браузер отправляет запрос локальному DNS-серверу (обычно роутер или провайдер).
2. Если провайдер не знает, запрос идёт вверх по иерархии: корневые серверы → серверы зоны `.com` → авторитативные серверы домена `example.com`.
3. **Результат:** браузер получает IP-адрес (например, `93.184.216.34`).

> **Важно:** результат DNS-запроса кэшируется на время **TTL** (Time To Live). Если TTL большой, а IP сервера сменился, пользователь может ходить на старый адрес, пока кэш не истечёт. Поэтому перед плановой сменой IP админы заранее снижают TTL.

## 3. TCP Handshake (установка соединения)

Браузер знает IP, теперь нужно установить надёжное TCP-соединение на порт `443` (для HTTPS).

```text
Браузер: SYN      (я хочу соединиться)
Сервер:  SYN-ACK  (я согласен)
Браузер: ACK      (принято)
```

Соединение установлено.

## 4. TLS Handshake (шифрование HTTPS)

Раз используется HTTPS, нужно договориться о шифровании, чтобы никто не подслушал трафик.

1. Браузер отправляет **Client Hello** (поддерживаемые версии TLS, шифры, а также **SNI** — имя сайта, к которому он подключается).
2. Сервер отвечает **Server Hello** и присылает свой **SSL-сертификат**.
3. Браузер проверяет сертификат: не истёк ли срок, выдан ли удостоверяющим центром, совпадает ли имя домена.
4. Стороны обмениваются ключами. С этого момента трафик зашифрован.

> **Что такое SNI (Server Name Indication)?** Это расширение TLS, которое позволяет браузеру в самом начале рукопожатия сообщить серверу, к какому именно домену он подключается. Без SNI на одном IP-адресе нельзя было бы разместить несколько HTTPS-сайтов с разными сертификатами. SNI решает эту проблему, позволяя серверу выбрать нужный сертификат ещё до завершения рукопожатия.

## 5. HTTP-запрос

Теперь браузер может безопасно попросить страницу.

```text
GET / HTTP/1.1   (или HTTP/2, или HTTP/3)
```

Заголовки:

| Заголовок | Назначение |
|---|---|
| `Host: example.com` | Какой сайт просим |
| `User-Agent: Chrome...` | Какой у меня браузер |
| `Cookie: ...` | Мои данные авторизации/настроек |
| `Accept: text/html` | Я хочу HTML |

### 5.1. Версии HTTP

- **HTTP/1.1:** Каждый запрос по умолчанию требует отдельного TCP-соединения (или последовательной обработки). Это создаёт **Head-of-Line (HOL) blocking** — если один запрос застрял, остальные ждут.
- **HTTP/2:** Вводит **мультиплексирование** (multiplexing) — несколько запросов и ответов передаются параллельно в рамках одного TCP-соединения, не блокируя друг друга. Также сжимает заголовки.
- **HTTP/3:** Работает поверх **QUIC** (протокол на базе UDP). Он решает проблему HOL-блокировки на уровне транспорта: потеря пакета в одном потоке не останавливает другие. HTTP/3 также быстрее устанавливает соединение (0-RTT).

## 6. Обработка на сервере (Nginx / Apache)

Запрос долетает до сервера, там его встречает веб-сервер (обычно Nginx или Apache).

- **Статичный файл** (картинка, CSS, просто HTML) — отдаётся сразу.
- **Нужна логика** (авторизация, поиск по базе) — Nginx работает как **reverse proxy** (обратный прокси) и передаёт запрос бэкенду (Python, PHP, Node.js) через внутренний порт (например, `8080`) или unix-socket.

### 6.1. Reverse Proxy vs Load Balancer (в чём разница)

Это два разных, но часто пересекающихся понятия:

| | **Reverse Proxy** | **Load Balancer** |
|---|---|---|
| **Что делает** | Принимает запрос от клиента и передаёт его на **один конкретный** бэкенд-сервер | Распределяет запросы между **группой** серверов, выполняющих одну и ту же функцию |
| **Когда нужен** | Даже если у тебя **один** сервер приложений (скрывает его, кэширует, терминирует SSL) | Когда у тебя **несколько** серверов и нужно распределить нагрузку |
| **Пример** | Nginx, Apache | Nginx (как балансировщик), HAProxy, облачные LB (AWS ELB) |

**Важно:** Nginx может выполнять обе роли одновременно. Один и тот же сервер Nginx может быть reverse proxy для бэкенда и балансировщиком для нескольких инстансов этого бэкенда.

## 7. Работа бэкенда (Backend & Database)

Бэкенд (например, на Python/Django) принимает запрос:
1. Выполняет код: проверяет куки, достаёт данные из БД (PostgreSQL/MySQL).
2. Собирает HTML-страницу (например, через шаблонизатор) и отдаёт её обратно Nginx'у.

## 8. HTTP-ответ (Response)

Nginx формирует ответ и отправляет его браузеру:
- **Статус-код:** `200 OK` (если всё хорошо) или `404 Not Found` (если бэкенд не нашёл страницу).
- **Заголовки:** `Content-Type: text/html`, `Set-Cookie` (если сервер хочет поставить новую куку).
- **Тело ответа:** сам HTML-код страницы.

## 9. Парсинг и рендеринг (Browser Rendering)

Браузер получает HTML и начинает его «читать»:
1. Строит DOM-дерево.
2. Находит внутри HTML ссылки на картинки, CSS-стили и JS-скрипты.
3. **Важно:** для каждой картинки и скрипта браузер снова выполняет шаги 2, 3, 4 и 5 (заново ищет IP, ставит TCP/TLS-соединение и делает запрос), если они не закэшированы. **Но с HTTP/2 и HTTP/3 эти запросы могут идти параллельно по одному соединению**, что значительно ускоряет загрузку.
4. Применяет CSS, выполняет JS и отрисовывает сайт на экране.

## 🛠️ Практика: как увидеть весь путь своими глазами

Самый простой способ — использовать `curl` с флагом `-v` (verbose). Он покажет каждый этап: DNS-резолвинг, TCP-соединение, TLS-рукопожатие и HTTP-обмен.

```bash
curl -v https://example.com
```

Для более точной диагностики (сколько времени занял каждый этап) можно использовать `curl -w`:

```bash
curl -sS -o /dev/null -w 'dns=%{time_namelookup}s tcp=%{time_connect}s tls=%{time_appconnect}s ttfb=%{time_starttransfer}s total=%{time_total}s code=%{http_code}\n' https://example.com
```
Эта команда покажет:
- `dns` — время на DNS-резолвинг.
- `tcp` — время на TCP-хендшейк.
- `tls` — время на TLS-рукопожатие.
- `ttfb` — время до первого байта ответа (Time To First Byte).
- `total` — общее время запроса.
- `code` — HTTP-код ответа.

Это отличный инструмент для диагностики: если `dns` большой — проблема в DNS, если `tls` большой — возможно, сервер медленно отдаёт сертификат, и т.д.
