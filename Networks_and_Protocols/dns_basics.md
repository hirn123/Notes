# Домены, делегирование и DNS

## 1. Что такое домен

- **Домен (доменное имя)** — удобное для человека буквенное обозначение IP-адреса. Компьютеры общаются по IP, например `93.184.216.34`, а человеку проще запомнить `example.com`.
- **Структура:** читается справа налево. `.com` — домен верхнего уровня (TLD), `example` — домен второго уровня (арендуется), `www` — поддомен.

## 2. Делегирование домена

**Простыми словами:** это передача прав на управление зоной домена от регистратора к твоим DNS-серверам.

**Технически:**
1. Покупаешь домен у регистратора (например, Reg.ru или Namecheap). Регистратор вносит запись в реестр домена верхнего уровня (TLD).
2. В панели регистратора указываешь NS-серверы, например `ns1.beget.com` и `ns2.beget.com`.
3. Регистратор передаёт эту информацию в реестр зоны `.com` или `.ru`.
4. Когда кто-то ищет твой домен, корневые серверы отвечают: «IP не знаю, но за этот домен отвечают серверы `ns1.beget.com`. Идите к ним».

**Суть:** ты говоришь глобальному интернету: «Я не хочу сам держать DNS-сервер — все вопросы по моему домену передавайте хостингу».

## 3. Как работает разрешение DNS (итеративные и рекурсивные запросы)

Это ключевой процесс, без которого домен не превратится в IP. Важно понимать два режима.

- **Рекурсивный запрос (Recursive)**: клиент (браузер, ОС) отправляет запрос своему **резолверу** (обычно DNS-серверу провайдера или публичному `8.8.8.8`) и ждёт от него **готовый ответ**. Резолвер берёт на себя всю работу: если он не знает ответа, он сам опрашивает другие серверы, пока не найдёт.
- **Итеративный запрос (Iterative)**: резолвер, в свою очередь, опрашивает корневые серверы, серверы зоны `.com` и авторитативные NS-серверы домена. Каждый из них отвечает не готовым IP, а **ссылкой на следующий сервер** («я не знаю, но спроси вон у того»). Так резолвер шаг за шагом доходит до нужной записи.

**Упрощённая цепочка для `example.com`:**
1. Браузер → резолвер: рекурсивный запрос «дай IP для example.com».
2. Резолвер → корневой сервер: итеративный запрос. Ответ: «Иди к серверам зоны `.com`».
3. Резолвер → сервер зоны `.com`: «Иди к NS-серверам example.com (например, `ns1.hosting.com`)».
4. Резолвер → `ns1.hosting.com`: «Какой A-адрес у example.com?» Ответ: `192.0.2.1`.
5. Резолвер возвращает IP браузеру и **кэширует** его на время TTL.

Именно поэтому при диагностике важно смотреть, **какой именно сервер** отвечает на запрос: локальный кэш, резолвер провайдера или авторитативный NS.

## 4. Утилиты `whois` и `dig`

| Утилита | Что показывает | Зачем нужно |
|---|---|---|
| `whois` | Административную информацию: регистратор, даты регистрации и окончания, статус, контакты владельца (если не скрыты) | Проверить владельца, срок домена, кому жаловаться на спам |
| `dig` | Техническую информацию: A-запись, MX, NS, TXT и т.д. | Диагностика: правильный ли IP, почтовые серверы, NS-серверы |

## 5. Основные DNS-записи

| Запись | Назначение | Пример / пояснение |
|---|---|---|
| `A` | Связывает домен с IPv4-адресом | `example.com -> 192.0.2.1` |
| `AAAA` | Связывает домен с IPv6-адресом | `example.com -> 2001:db8::1` |
| `CNAME` | Псевдоним (алиас) для другого домена | `www.example.com -> example.com`. Нельзя ставить на apex-домен (сам `example.com`) |
| `MX` | Указывает сервер, который принимает почту. Чем меньше число, тем выше приоритет | `example.com -> mail.example.com (10)` |
| `NS` | Указывает серверы, которые хранят настройки зоны | `example.com -> ns1.hosting.com` |
| `TXT` | Текстовая запись произвольного содержания. Используется для **SPF, DKIM, DMARC** и подтверждения владения доменом | `"v=spf1 include:_spf.google.com ~all"` |
| `PTR` | **Обратная запись**: IP → домен. Используется для проверки «честности» почтового сервера | `192.0.2.1 -> mail.example.com` |

### Почему TXT-записи критичны для почты

Если письма с твоего домена попадают в спам, почти всегда проблема в трёх TXT-записях:
- **SPF (Sender Policy Framework)** — список IP/серверов, которым **разрешено** отправлять почту от имени домена. Пример: `v=spf1 include:_spf.google.com ~all` (разрешает Google, остальным — мягкий отказ).
- **DKIM (DomainKeys Identified Mail)** — **цифровая подпись** письма. Публичный ключ публикуется в TXT-записи на поддомене вида `selector._domainkey.example.com`. Получатель проверяет подпись и понимает, что письмо не подделано.
- **DMARC (Domain-based Message Authentication, Reporting and Conformance)** — **политика** для получателя: что делать, если SPF/DKIM не прошли (ничего / в спам / отклонить). Пример: `v=DMARC1; p=quarantine; rua=mailto:dmarc@example.com`.

Без этих записей крупные почтовые провайдеры (Gmail, Яндекс, Mail.ru) будут относиться к письмам с подозрением. Поэтому вопрос «клиент говорит, что письма в спаме» — это почти всегда про DNS, а не про сам почтовый сервер.

## 6. TTL и кэширование (почему изменения «не сразу»)

У каждой DNS-записи есть параметр **TTL (Time To Live)** — время в секундах, в течение которого резолверы и клиенты могут хранить запись в кэше.

- **Маленький TTL (например, 300 секунд)** — изменения распространяются быстро, но резолверы чаще ходят к авторитативным серверам (больше нагрузки).
- **Большой TTL (например, 86400 секунд = сутки)** — меньше нагрузки на DNS, но при смене IP старый адрес может «залипнуть» в кэшах на часы.

Поэтому **перед плановой сменой IP или переездом** опытные админы **заранее снижают TTL** (например, до 300 секунд), ждут, пока старый TTL истечёт, меняют запись, а потом возвращают TTL обратно. Это классический сисадминский приём, который часто спрашивают на собеседованиях.

## 7. Диагностика DNS (что делать, если «сайт не открывается»)

Порядок действий сисадмина при проблемах с DNS:

1. **Проверить, что отдаёт публичный резолвер** (не кэш локальной машины):
   ```bash
   dig @8.8.8.8 example.com A
   ```
   Флаг `@8.8.8.8` заставляет `dig` обратиться напрямую к DNS Google, минуя локальный кэш.

2. **Проверить делегирование (NS-записи)**:
   ```bash
   dig example.com NS
   ```
   Если NS-серверы не совпадают с теми, что указаны у регистратора, — домен делегирован не туда.

3. **Проследить всю цепочку от корня**:
   ```bash
   dig +trace example.com
   ```
   Покажет, как резолвер идёт от корневых серверов до авторитативных.

4. **Проверить обратную запись (PTR)** для почтового сервера:
   ```bash
   dig -x 192.0.2.1
   ```
   Если PTR не совпадает с именем, которое сервер представляет в HELO/EHLO, многие почтовые системы будут отклонять письма.

5. **Проверить TXT-записи (SPF/DKIM/DMARC)**:
   ```bash
   dig example.com TXT
   ```

**Важно:** `nslookup` и `host` тоже работают, но `dig` даёт больше деталей (TTL, авторитативный ли ответ, какой сервер ответил) и считается стандартом для диагностики.

## 8. Домены, IP и DNS на практике

### 8.1. Может ли сайт работать без домена?
**Да, может.** Для доступа к сайту по IP-адресу не нужен домен. Браузер может открыть `http://93.184.216.34`, и сервер ответит, если он настроен на обработку запросов по этому IP. Домен нужен только для удобства людей и для работы некоторых функций (например, HTTPS-сертификаты выдаются на домены, а не на IP). На практике сайты по IP работают, но это неудобно для пользователей и проблематично для SEO.

### 8.2. Может ли одному доменному имени соответствовать несколько IP-адресов?
**Да.** Для этого в DNS-зоне домена создаётся несколько **A-записей** (или AAAA для IPv6) с одинаковым именем, но разными IP-адресами. 
*   **Как это работает:** DNS-сервер при каждом запросе «перебирает» IP-адреса по кругу (алгоритм **Round-robin**). Первый посетитель получает один IP, второй — другой, третий — третий и т.д.
*   **Зачем это нужно:** Это простейший способ балансировки нагрузки (Load Balancing). Если у тебя два сервера, ты можешь направить часть трафика на один, а часть — на другой. Минус — DNS не проверяет, жив ли сервер, поэтому может отправить пользователя на упавший узел.

### 8.3. Может ли одному IP-адресу соответствовать несколько доменных имен?
**Да, и это основа современного хостинга.** На одном IP-адресе может работать сотня сайтов (виртуальный хостинг).
*   **Как сервер понимает, какой сайт показать?**
    *   **Для HTTP (порт 80):** Браузер передаёт в заголовке запроса `Host: example.com`. Веб-сервер (Nginx/Apache) смотрит на этот заголовок и выбирает нужный сайт из своей конфигурации.
    *   **Для HTTPS (порт 443):** Заголовок `Host` зашифрован, поэтому сервер не может его прочитать до расшифровки. Здесь используется расширение **SNI (Server Name Indication)**. Браузер ещё до установки шифрованного соединения сообщает серверу, к какому домену он обращается (`Client Hello` содержит имя домена). Сервер выбирает правильный SSL-сертификат и только потом завершает рукопожатие. Без SNI на одном IP нельзя было бы разместить несколько HTTPS-сайтов с разными сертификатами.

### 8.4. Можно ли открыть сайт без DNS-запроса? Зачем нужен файл hosts?
**Да, можно.** Для этого используется файл **`hosts`** (`/etc/hosts` в Linux, `C:\Windows\System32\drivers\etc\hosts` в Windows).
*   **Принцип работы:** Когда ты вводишь домен в браузере, операционная система **сначала** проверяет файл `hosts`, и только если там нет записи — идёт в DNS. Если ты добавишь строку `192.0.2.1 example.com`, то браузер пойдёт по этому IP, **игнорируя DNS**.
*   **Зачем это нужно:**
    1.  **Для тестирования:** Разработчик может проверить сайт на новом сервере, не меняя реальные DNS-записи.
    2.  **Для блокировки:** Сисадмин может прописать `0.0.0.0 spam-site.com`, чтобы заблокировать доступ к сайту на уровне ОС.
    3.  **Для локальной разработки:** Указать `127.0.0.1 myapp.local`.

## 9. Практика

### 9.1. Базовые команды
```bash
whois phone-test.ru
```
Пример:
- `registrar: BEGET-RU`
- `created: 2021-12-07T08:29:53Z`
- `paid-till: 2026-12-07T08:29:53Z`
- `free-date: 2027-01-07`

```bash
dig A phone-test.ru
```
Пример: `A — 45.130.41.127`

```bash
dig MX phone-test.ru
```
Пример:
- `MX 10 mx1.beget.com.`
- `MX 20 mx2.beget.com.`

```bash
dig NS phone-test.ru
```
Пример:
- `NS harlee.ns.cloudflare.com.`
- `NS sonny.ns.cloudflare.com.`
